# Rebomi PRD 정리·변경

제품 요구사항의 기준은 `docs/product.md`와 `docs/features/*.md`다. 이 스킬은 변경을 **한곳에만** 반영하고, 구현자가 정책을 추측하지 않게 만든다.

## 먼저 구분한다

| 요청 | 처리 |
| --- | --- |
| 작은 버그, 명백한 오타, 동작이 그대로인 리팩터링 | 이 스킬을 쓰지 않는다. PRD를 새로 만들지 않는다 |
| 문서 정리(표현, 링크, 구조) — 요구사항의 뜻이 그대로 | 고치고 끝낸다. 결정을 묻지 않는다 |
| 제품 정책 변경(범위, 우선순위, 동작 규칙, 한도, 완료 조건의 뜻) | 아래 절차 |

## 읽는 범위

전체를 읽지 않는다. 시작점이지 제한선은 아니다.

| 변경 | 읽을 것 |
| --- | --- |
| 한 기능의 동작 | 그 기능 문서 + 그 문서 "의존"에 적힌 문서의 해당 절 |
| 제품 방향·출시 범위·우선순위 | `docs/product.md` + 영향받는 기능 문서 |
| 상태·인증·API 등 공통 계약 | `docs/architecture.md` + 영향받는 기능 문서 |
| 미결정 사항 결정 | `docs/product.md` §9의 그 행 + "영향" 열의 문서 |

`docs/PRD-v0.5.md`는 이력용 스냅샷이다. 고치지 않는다. 원문 확인이 필요할 때만 해당 절을 읽는다.

## 절차

1. **자리 찾기** — 요구사항이 어느 기능 문서에 속하는지 정한다. 여러 기능에 걸치면 규칙은 한 문서에 두고 나머지는 링크한다. 맞는 문서가 없으면 새 기능 문서를 제안하되 빈 문서를 형식적으로 만들지 않는다.
2. **현재 구현 확인** — 관련 코드가 이미 있으면 본다. 문서와 코드가 다르면 어느 쪽이 맞는지 단정하지 말고 차이를 적는다.
3. **영향 확인** — 공통 상태 다섯 축(`architecture.md` §4), 다른 기능의 요구사항 ID, 열린 Issue에 영향이 있는지 본다.
4. **기록** — 기능 문서 형식(목적 / 범위 / 플랫폼별 역할 / 흐름 / 규칙·예외 / 완료 조건 / 의존 / 미결정)을 따른다.
   - 새 요구사항은 그 문서의 다음 ID를 준다(`CAP-12`). **기존 ID를 재사용하거나 번호를 다시 매기지 않는다** — Issue가 ID로 참조한다.
   - 완료 조건은 검증 가능한 문장으로 쓴다.
   - 사용자가 말하지 않은 것을 채워 넣었으면 `[제안]`으로 표시한다.
5. **미결정 처리**
   - 사용자가 결정했다: `product.md` §9에서 그 행을 지우고, 결정 내용을 해당 기능 문서의 규칙·완료 조건으로 옮긴다. 다른 문서의 `D-xx` 참조를 찾아 고친다(`Grep "D-0X"`).
   - 답이 없는 정책을 발견했다: `product.md` §9에 다음 번호로 추가하고 기능 문서에서는 ID로만 참조한다. **임의로 정하지 않는다.**
6. **Issue 반영** — 변경이 열린 Issue의 범위나 완료 조건을 바꾸면 사용자에게 어떤 Issue가 영향받는지 알린다. 결정으로 `needs-decision`이 풀린 Issue가 있으면 본문의 미결정 사항을 갱신하고 `status:todo`로 바꾼다(`docs/workflow/github.md`).

## 지킬 것

- **P0를 임의로 P1으로 내리지 않는다.** 문서 분리, 구현 순서 조정, 출시 범위 축소는 서로 다른 일이다. 범위 축소가 필요해 보이면 변경하지 말고 별도 제안으로 사용자에게 묻는다.
- 같은 규칙을 두 문서에 쓰지 않는다. 한 곳에 쓰고 링크한다.
- 원문 PRD에 기술명이 있다는 이유로 도입을 확정하지 않는다. 기술 선택은 `architecture.md` §9에서 "확정"과 "후보"로 나눈다.
- 문서를 고친 뒤 깨진 상대 링크와 사라진 ID 참조가 없는지 확인한다.

## 끝낼 때 보고

무엇을 어느 문서의 어느 ID로 바꿨는지, 새로 생기거나 풀린 미결정 사항, 영향받는 Issue.
