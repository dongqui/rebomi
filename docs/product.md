## 1. 문제와 비전

저장은 쉬워졌지만 저장 이후의 경험은 나아지지 않았다. 사용자는 수백~수천 개를 저장하고도

- **A. 다시 보지 않는다** — 잊어버리고, 새 자료에 묻히고, 무엇부터 볼지 모르고, 정리 자체가 부담이다.
- **B. 다시 찾지 못한다** — 제목·출처·정확한 키워드를 기억하지 못해 결국 다시 검색한다.

> 저장한 콘텐츠를 잊지 않도록 다시 보여주고, 필요한 순간 빠르게 찾아준다.

| --- | --- | --- |

| Organize — 관리 | 중요한 것은 보관하고 불필요한 것은 제거한다 | [library](features/library.md) |

### 포지셔닝

wedge는 재노출이다. 요약과 의미 검색은 여러 제품이 이미 제공하므로 그것만으로는 갈아탈 이유가 되지 않는다. "저장한 것을 잊지 않게 해주는 서비스"로 포지셔닝하고, 검색·요약은 그 약속을 지키는 기반 기능으로 둔다.

| 제품 | AI 요약 | 의미 검색 | 재노출 | 비고 |
| --- | --- | --- | --- | --- |
| Pocket | 없음 | 없음 | 없음 | 2025년 7월 종료. 이탈 사용자가 1차 타깃 |
| Raindrop.io | 없음 | 제한적 | 없음 | 폴더·태그 중심 정리 도구 |
| mymind | 자동 태깅 | 있음 | 없음 | 정리 없이 저장, 유료 |
| Readwise Reader | 있음 | 제한적 | 하이라이트만 | 읽은 것의 복습 |
| Recall | 있음 | 있음 | 복습 카드 | 지식 그래프, 간격 반복 |
| **Rebomi** | 있음 | 하이브리드 | **핵심** | 읽기를 강요하지 않는 재노출, 북마크 대량 가져오기 |

Readwise·Recall은 "읽은 것의 암기", Rebomi는 "읽지 않은 것의 재발견"을 다룬다. 경쟁 정보는 2026년 11월 공개 자료 기준이며 출시 전 재확인한다.

## 2. 핵심 원칙

1. 저장은 빠르고 간편해야 하며, 저장하는 순간 본문까지 확보한다.
2. 다시 읽도록 강요하지 않는다. Inbox는 비우지 않아도 쌓이지 않는다.
3. 제목을 잊어도 내용으로 찾을 수 있어야 한다.
4. 저장된 자료를 주기적으로 다시 발견할 기회를 준다. **이것이 제품의 존재 이유다.**
5. AI는 자료를 이해하고 찾는 일을 돕되, 원본을 대체하지 않는다.
6. 보관할 자료와 삭제할 자료를 쉽게 결정하도록 돕는다.
7. 사용자의 비용(시간, 돈, 개인정보)을 사용자가 통제할 수 있게 한다.
8. 장기적으로는 읽거나 듣는 등 원하는 방식으로 소비할 수 있게 발전한다.

**최종 목표:** 저장한 콘텐츠를 잊지 않고, 필요할 때 다시 찾아 실제로 활용하게 만드는 것.

## 3. 타깃과 시나리오

콘텐츠를 자주 저장하지만 다시 확인하거나 찾는 데 어려움을 겪는 개인 사용자(B2C).

- 브라우저에 북마크 수백~수천 개를 쌓아둔 사람
- Reddit, YouTube, X 등에서 자료를 자주 저장하는 사람
- 공부하거나 새 분야를 탐색하며 자료를 모으는 사람
- 저장한 글을 기억하지 못해 반복 검색하는 사람
- Pocket 종료 이후 대체 서비스를 찾지 못한 사람

| 시나리오 | 흐름 | 관련 기능 |
| --- | --- | --- |
| **A — 재발견** | Reddit 앱에서 공유 메뉴로 저장(본문 함께 전송) → 자동 요약 → 일주일 뒤 홈에 다시 표시 → 요약 확인 후 원문 열람 → 보관 또는 삭제 | capture, summary, resurfacing, library |
| **B — 검색** | 제목·출처를 잊은 자료를 "Next.js에서 여러 서비스를 독립적으로 배포하는 방법에 관한 글"로 검색 → 의미적으로 관련된 자료 → 요약 보고 원문 열기 | search, summary |
| **C — 기존 북마크 정리** | Chrome 북마크 1,300개 가져오기 → 제목·URL·본문 수집, 죽은 링크 별도 표시 → 요약 생성 → 재노출에는 폴더 단위로 골라 포함 → 검색·탐색하며 죽은 링크와 오래된 자료 일괄 정리 | import, summary, resurfacing, library |

### P1 — MVP 이후

검색 고급 필터·품질 개선·개인화 / 이메일 재노출 다이제스트 / 행동 기반 재노출 추천 / 유사 콘텐츠 탐지 / 태그·사용자 폴더 / 요약 고도화(핵심 포인트, 재생성, 여러 길이, YouTube 자막 기반 상세 요약) / 다른 브라우저 지원 / 관심사·검색 주제 기반 재노출, 재노출 날짜 직접 지정 / 출처별 필터, 중복·유사 콘텐츠 정리, 오래된 콘텐츠 일괄 정리 추천.

### P2 — 장기 확장

MVP에서 수집·검색·재노출의 가치를 검증한 뒤 수요에 따라 확장한다.

- **오디오 요약·브리핑** — 개별 오디오 요약, 여러 콘텐츠를 결합한 브리핑, 주간 오디오 다이제스트, 재노출 콘텐츠 듣기, 기본 플레이어. 단순 낭독보다 설명형 오디오를 지향
- **AI 지식 검색 챗봇** — 저장 콘텐츠 기반 답변과 원문 연결 (RAG)
- **콘텐츠 간 자동 연결** — 비슷한 콘텐츠 연결과 관련 자료 추천
- **지식 카드·학습** — 복습 카드, 퀴즈
- **지식 그래프** — 콘텐츠·주제 관계 시각화

## 7. 개발 단계와 게이트

**[원문에서 확인되는 것]**

- 네 단계를 순서대로 진행하고 각 단계 끝에 완료 조건을 게이트로 둔다 (4단계, 4게이트).
- 사용자 테스트는 Phase 2 끝과 Phase 3 끝에 각각 있다.
- Phase 2 완료 시 **웹만으로** 1차 테스트를 해 H1(검색)·H3(요약)을 검증한다. 모바일 완성을 기다리지 않는다.
- Phase 2에서 한·영 혼합 쿼리 100개로 검색 모델을 비교 평가해 확정하고, 요약·임베딩 1건당 비용을 측정한다. 지표 목표치도 Phase 2 테스트 후 정한다.
- Phase 3은 재노출을 담는다(H2 2차 테스트, H4).
- Phase 4에서 H5·H6을 검증하고, 비용 측정 결과로 무료 한도를 확정한다.

**[확인되지 않는 것 — D-09]** 원문 7장의 로드맵 본체는 임베디드 콘텐츠로만 있었고 Markdown에는 표시만 남아 있다. 저장소 어디에도 없다. 단계별 포함 기능과 게이트의 정확한 완료 조건은 **복원되지 않았다.**

**[제안] 단계 구성** — 위 확인 사항과 모순되지 않게 채운 안이다. 확정 전까지 게이트로 쓰지 않는다.

| 단계 | 제안 내용 | 게이트 (원문 근거가 있는 부분만) |
| --- | --- | --- |
| Phase 1 | 계정, 웹 URL 저장, Chrome 확장 저장, 목록·상태 관리 기반, 비동기 처리 파이프라인 | 원문 근거 없음 |

| Phase 3 | 재노출 선정·홈 피드·빈도 설정·푸시, iOS·Android 공유 저장 | 2차 사용자 테스트(H2), H4 |

## 8. 성공 지표와 가설

### North Star — 주간 활성 사용자 1인당 재활용 수

"재활용"은 다음 중 하나다.

- 재노출 카드에서 원문 열기, 보관하기, 나중에 다시 보기 중 하나를 실행
- 검색 결과에서 원문 열기
- 재노출 카드를 펼쳐 요약을 읽은 뒤 5초 이상 체류

삭제와 재노출 중단은 재활용이 아니라 **정리 성공**으로 따로 센다. 같은 콘텐츠·같은 사용자의 반복 행동을 어떻게 셀지는 **D-07**.

| 묶음 | 지표 | 계측이 필요한 기능 |
| --- | --- | --- |
| 재노출 (wedge) | 확인률(카드 펼침/노출), 원문 열람률·보관률·삭제률, 알림 해제율, 빈도 하향률, 주 1회 이상 피드 확인 사용자 비율 | resurfacing |
| 검색 | 검색 실행 사용자 비율, 결과 클릭률, 검색 후 원문 재열람 비율, 실패율(결과 없음 또는 클릭 없이 재검색), 첫 클릭까지 시간 | search |
| 전체 | WAU, 4주 유지율, 사용자별 저장 수, 본문 확보 비율, 대량 가져오기 이용률, 가져오기 후 정리 화면 사용률, Free→Pro 전환율 | capture, import, library, billing |

목표치는 Phase 2 사용자 테스트 후 설정한다.

### 검증 가설

| 가설 | 내용 | 검증 시점 | 판단 지표 |
| --- | --- | --- | --- |
| H1 — 검색 | 자연어 검색이 기존 북마크 검색보다 원하는 콘텐츠를 더 쉽게 찾게 한다 | Phase 2 후 1차 테스트 | 과제 성공률, 첫 클릭까지 시간 |
| **H2 — 재노출** | 재노출된 콘텐츠는 그렇지 않은 콘텐츠보다 다시 확인·활용될 가능성이 높다. **핵심 가설** | Phase 3 후 2차 테스트 | 재노출 vs 미노출 콘텐츠의 4주 내 원문 열람률 |
| H3 — AI 요약 | 짧은 요약으로 원문을 열지 않고 내용을 판단할 수 있다 | Phase 2 후 1차 테스트 | 요약만 보고 보관/삭제를 결정한 비율 |
| H4 — 수집 경험 | 클라이언트 캡처를 포함한 원클릭·공유창 저장이 앱 이동보다 간편하다 | Phase 3 | 저장 완료율, 본문 확보 비율 |
| H5 — 지속 사용 | 재노출과 검색을 함께 주면 지속 사용 도구로 인식한다 | Phase 4 | 4주 유지율, 주 1회 이상 재노출 피드 확인 비율 |
| H6 — 북마크 구조조정 | 대량 가져오기 + 정리 화면을 거친 사용자의 유지율이 더 높다 | Phase 4 | 가져오기 사용자 vs 비사용자의 4주 유지율 |

## 9. 미결정 사항

답이 필요한 제품 결정을 여기 한곳에 모은다. 기능 문서는 ID로만 참조한다. 결정되면 이 표에서 지우고 해당 기능 문서에 규칙으로 옮긴다. 결정에 영향받는 Issue만 실행 대기(`needs-decision`)로 두고, 나머지 작업은 멈추지 않는다.

| ID | 결정할 것 | 근거가 되는 원문의 충돌·공백 | 영향 |
| --- | --- | --- | --- |
| D-01 | 정리 화면이 P0에서 다루는 범위 | 4.5·6장은 P0를 "링크 소멸 일괄 삭제 제안"으로 적는다. 5.5는 정리 화면이 중복·오래된 미확인 콘텐츠도 다룬다고 적는다. 그런데 4.5는 중복·유사 정리와 오래된 콘텐츠 정리 추천을 P1로 둔다 | library LIB-7 |
| D-02 | 기본 푸시가 P0에서 누구에게 제공되는가 | 6장은 "기본 푸시 알림"을 P0로, 4.4는 "동의한 경우 모바일 푸시"로 적는다. 9장은 Free=홈 피드, Pro=홈 피드+푸시로 적는다 | resurfacing RES-7, billing BILL-1 |
| D-03 | 저장 개수 한도 초과와 AI 처리 한도 초과 시 각각의 동작 | 9장은 "대량 가져오기의 한도 초과분은 메타데이터만 등록"만 적는다. 직접 저장이 500개를 넘을 때, 직접 저장이 월 AI 한도를 넘을 때의 동작은 없다. Free 가져오기 500개 초과분 처리와 "최초 1회"의 판정도 없다 | billing BILL-2~3, capture, import |
| D-04 | 일시적 접근 실패와 링크 소멸의 구분 | 4.1은 "응답 없음·404·도메인 소멸"을 링크 소멸로 분류한다. 재시도 횟수·기간, 403·봇 차단·타임아웃의 처리, 소멸 판정 후 되살아난 링크의 복구가 없다(4.4는 링크 소멸의 재노출 제외를 "변경 불가"로 적는다) | import IMP-5, architecture 링크 상태 |
| D-05 | 재노출의 정확한 기본값 | "주 2~3회, 회당 3~5개"는 범위다. 홈의 "오늘의 재노출 3~5개"와 주 2~3회의 관계, 사용자가 고를 수 있는 빈도 선택지, "나중에 다시 보기"의 기간, 후보가 모자랄 때의 동작, "최근 7일 내 확인"의 정의가 없다 | resurfacing RES-1, RES-5~6 |
| D-06 | 내보내기와 계정·데이터 삭제의 출시 범위 | 5.6 설정과 11.8 대응에는 있으나 6장 P0 표에는 없다 | account ACC-4~5 |
| D-07 | 재활용 지표의 중복 집계 기준 | 10장은 재활용 행동을 정의하지만, 한 콘텐츠에 여러 행동을 하거나 같은 주에 반복한 경우의 집계 단위가 없다 | 계측 전반 |
| D-08 | 모바일의 로그인 방식과 동기화의 반영 시점 | 로그인 수단(Google·Apple), 세션 방식(액세스+갱신 토큰), 직접 구현, 계정 연결 기준은 2026-11-10에, 확장의 웹 로그인 재사용(ACC-9)은 2026-11-13에 결정해 [account](features/account.md) §4로 옮겼다. 남은 것: 모바일 로그인 흐름의 세부, "동기화"가 뜻하는 반영 시점 | account ACC-3, capture CAP-11, 모바일 |
| D-09 | Phase별 포함 기능과 게이트 완료 조건 | 7장 로드맵 본체가 유실되었다 (위 7장) | 개발 순서 |
| D-10 | 결제 수단과 요금 | 8장은 "Stripe 또는 앱 내 결제"로 적는다. Pro 가격, 모바일 앱 내 결제 여부, 해지·다운그레이드 시 한도 초과 데이터의 처리가 없다 | billing BILL-4 |
| D-11 | Inbox의 "나중에 보기"와 재노출의 "나중에 다시 보기"가 같은 동작인가 | 5.3과 4.4가 서로 다른 이름을 쓰고 동작 정의가 없다 | library, resurfacing RES-5 |
| D-12 | 공개 페이지 판정과 캐시 공유 범위 | 9장은 동일 URL의 요약·임베딩을 "공개 페이지에 한해" 사용자 간 공유한다고 적는다. 공개 여부의 판정 기준이 없다(클라이언트 캡처 본문은 로그인 페이지일 수 있다) | summary SUM-6, architecture 비용 통제 |
| D-13 | 요약 언어의 기준 | 4.2는 "사용자 언어에 맞는 요약(한국어·영어)"으로 적는다. 사용자 설정 언어인지 콘텐츠 언어인지 없다 | summary SUM-2 |
| D-14 | 휴지통에 있는 URL을 다시 저장할 때의 동작 | 4.1은 "중복이면 새 콘텐츠를 만들지 않는다"만 적고, 4.5는 휴지통을 "복구할 수 있고 30일 후 영구 삭제"로 적는다. 삭제한 URL을 다시 저장하면 중복으로 알릴지(휴지통에 있다는 안내 포함 여부), 되살려 Inbox로 보낼지, 새 콘텐츠로 만들지가 없다. 결정 전까지 저장 API는 보관 상태와 무관하게 중복으로 응답한다 | capture CAP-6, library LIB-4 |
| D-15 | 이미 저장한 URL을 다시 저장하면 저장일을 지금으로 갱신하는가 | 4.1은 "중복이면 새 콘텐츠를 만들지 않는다"만 적는다. 다시 저장한 콘텐츠가 목록 맨 위로 올라오는지, 저장일이 바뀌는지가 없다. 방향은 "갱신한다"로 기울어 있다(2026-11-13, 다시 저장하려 한 것이 새 의도라는 이유). 남은 것: Inbox 30일 자동 보관과 재노출 시점의 기준일도 함께 초기화되는지, 처음 저장한 날을 따로 남기는지, 보관됨 상태의 콘텐츠를 다시 저장하면 Inbox로 돌아오는지(D-14와 맞물린다). 결정 전까지 중복 저장은 기존 콘텐츠를 바꾸지 않고 목록 순서도 그대로다 | capture CAP-6, library LIB-1~3, resurfacing |

기술 선택의 미정 사항(임베딩 모델, LLM, 푸시·결제 제공자)은 [architecture.md](architecture.md#9-확정-기술과-검증할-후보)에 있다.
