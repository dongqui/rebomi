# 대기 명단 랜딩 · Issue 초안

**상태: 초안. 사용자 승인 전이며 GitHub에 등록하지 않았다.**

## 묶음의 목표

**웹의 첫 주소에 대기 명단 랜딩을 두고, 설문의 답을 고를 때마다, 그리고 이메일을 서버에 저장한다.** 기준은 `docs/features/waitlist.md`(2026-11-17 추가)와 디자인 프로젝트의 `RebomiLanding`이다.

## 나눈 기준

- 서버(저장)와 웹(화면)은 혼자서 검증된다. 계약(`packages/api-contract`)은 서버 Issue에 넣는다.
- 웹 Issue가 실제 API에 연결해 등록까지 확인한다 — 연결 검증을 따로 떼지 않는다.
- 주소 이전(`/` → `/app`)은 랜딩과 한 화면 변경이라 웹 Issue에 넣는다.

- **라벨:** `status:todo`
- **목표:** 로그인 없이, 브라우저가 만든 응답 ID로 설문 답을 그때그때 저장하고 마지막에 이메일을 같은 응답에 저장하는 API를 만든다.
- **PRD 참조**
  - `docs/features/waitlist.md` §2 WAIT-4, WAIT-8 / §4 사용자 흐름 / §5 동작 규칙 / §6 완료 조건
  - `docs/architecture.md` §2 패키지 경계, §8 개인정보
- **범위**
  - **포함**
    - `api-contract`에 응답 저장 요청·응답과 설문 답의 고정 키 정의
    - 설문 응답 테이블과 마이그레이션
    - 응답 저장 경로(인증 없음): 클라이언트가 만든 ID로 없으면 만들고 있으면 갱신, 일부 질문만 답한 상태 허용, 이메일 정규화
    - `api-client`에 응답 저장 호출 추가
    - `architecture.md` §1·§8 갱신
  - **제외**
    - 랜딩 화면(B)
    - 방문·유입 기록, 광고 유입 파라미터 저장 (D-17)
    - 확인 메일·초대 메일 발송
    - 명단 조회·내보내기 화면이나 API
  - **설계에서 사용자에게 묻는 것**
    - 경로와 요청 모양(한 경로에 지금까지의 답 전체를 보내는 갱신 / 질문별 부분 갱신), 응답 ID의 형식
    - 테이블·컬럼 이름과 답의 저장 모양(질문별 컬럼 / JSON 한 컬럼), 처음 만든 시각과 마지막 갱신 시각
    - 설문 답의 고정 키 값
    - 이메일을 낸 뒤의 응답을 더 고칠 수 있는지
    - 과도한 요청 제한의 방식과 한도 (`waitlist.md` §5 [제안]), 새 의존성 여부
    - 응답 모양(저장된 내용을 돌려주지 않는다 — `waitlist.md` §5 [제안])
- **완료 조건**
  - [ ] 새 ID로 첫 질문의 답만 보내면 응답이 생기고, 답·언어·헤드라인이 이메일 없이 DB에 남는다
  - [ ] 같은 ID로 다시 보내면 응답이 늘지 않고 그 응답의 답이 갱신된다 (답을 바꾸거나 복수 선택에서 뺀 것 포함)
  - [ ] 같은 ID로 이메일을 보내면 그 응답에 이메일이 남는다. 이메일은 앞뒤 공백을 떼고 소문자로 저장된다
  - [ ] 로그인하지 않은 요청으로 위가 모두 된다
  - [ ] 서로 다른 ID로 같은 이메일을 내면 응답이 두 개 남는다
  - [ ] 이메일 형식이 틀리거나, 정의되지 않은 답 키이거나, ID 형식이 틀린 요청은 400 `VALIDATION_FAILED`이고 저장·갱신되지 않는다
  - [ ] API의 어떤 응답도 저장된 이메일이나 답을 돌려주지 않는다
  - [ ] 응답 저장은 `users` 행을 만들지 않는다
  - [ ] 설계에서 정한 한도를 넘는 반복 요청은 거부된다
  - [ ] `pnpm lint && pnpm typecheck && pnpm test && pnpm build`가 통과한다
- **검증 방법:** `api-contract`·`api-client` 단위 테스트, api 통합 테스트(실제 Postgres)
- **선행 Issue:** 없음
- **미결정 사항:** 없음 (D-16은 공개 배포 전에 필요하며 구현을 막지 않는다)

### B. [web] 대기 명단 랜딩 페이지와 `/app` 이전

```
<!-- rebomi-issue | prd: docs/features/waitlist.md | req: WAIT-1,WAIT-2,WAIT-3,WAIT-4,WAIT-5,WAIT-6,WAIT-7,WAIT-8 -->
```

- **라벨:** `status:todo`
- **목표:** `/`에 디자인대로 랜딩을 두고, 등록 대화상자에서 실제로 등록되게 한다. 로그인한 화면은 `/app`으로 옮긴다.
- **PRD 참조**
  - `docs/features/waitlist.md` §2 WAIT-1~8 / §4 사용자 흐름 / §5 동작 규칙 / §6 완료 조건
  - `docs/features/account.md` §3 웹의 역할 (로그인 화면과 세션은 그대로)
  - 디자인: `RebomiLanding`, `rebomi-tokens.css`, `RbCard`(휴대폰 안 화면)
- **범위**
  - **포함**
    - 랜딩 페이지(히어로, 문제 제기, 하는 일 세 가지, "차분하게", 사용 방법, 마지막 등록 버튼, 푸터)
    - 등록 대화상자(질문 네 개 → 이메일 → 완료)와 A의 API 연결: 열릴 때 응답 ID 생성, 답을 고를 때마다 저장, 이메일 저장
    - 한국어·영어 문구와 브라우저 언어에 따른 선택, 헤드라인 세 가지의 주소 지정
    - 라이트·다크(기기 설정), 톤 "웜 페이퍼"
    - 디자인 토큰과 Pretendard 글꼴을 `apps/web`에 도입 (랜딩에 필요한 범위)
    - 히어로 휴대폰 안의 정적 화면
    - 로그인한 화면을 `/app`으로 이전: 로그인 뒤 이동, 보호 경로, 로그아웃 뒤 이동
    - `architecture.md` §1 갱신
  - **제외**
    - 로그인한 화면(`/app`)의 디자인 적용 — 주소만 옮긴다
    - 휴대폰 안 화면의 조작
    - 방문·유입 기록 (D-17)
    - 톤·테마를 방문자가 바꾸는 UI
  - **설계에서 사용자에게 묻는 것**
    - 스타일 방식(지금은 인라인 스타일뿐이다 — CSS 파일 도입 여부와 위치), 토큰을 어디까지 가져올지
    - 헤드라인을 고르는 주소의 모양(파라미터 이름과 값)
    - 랜딩을 서버에서 그릴지와 언어 판정 위치(요청의 `Accept-Language` / 브라우저)
    - 로그아웃 뒤와 `/login`에서 이미 로그인한 경우의 이동 위치
    - 검색 엔진 노출 여부와 메타 정보(제목·설명·공유 이미지)
    - 완료 화면을 본 뒤 등록 버튼을 다시 누르면 새 응답으로 시작하는지 (`waitlist.md` §5 [확인 필요])
    - 하나만 고르는 질문은 고르면 0.2초 뒤 넘어간다 — 저장 요청을 기다릴지
- **완료 조건**
  - [ ] 로그인하지 않은 브라우저로 `/`를 열면 로그인 화면으로 넘어가지 않고 랜딩이 보인다
  - [ ] 로그인한 사용자는 `/app`에서 저장과 목록을 지금과 똑같이 쓴다. 로그인하지 않고 `/app`을 열면 로그인 화면으로 가고, 로그인에 성공하면 `/app`으로 간다
  - [ ] 브라우저 언어가 한국어면 한국어 문구, 아니면 영어 문구가 보인다
  - [ ] 주소로 헤드라인을 지정하면 그 헤드라인이, 지정이 없거나 모르는 값이면 기본 헤드라인이 보인다
  - [ ] 등록 버튼 → 질문 네 개 → 이메일 → 완료까지 키보드만으로 진행할 수 있다. 닫았다 다시 열면 하던 단계에서 이어진다
  - [ ] 이메일 형식이 틀리면 서버로 보내지 않고 그 자리에서 알린다
  - [ ] 대화상자를 열기만 하고 닫으면 서버로 아무것도 보내지 않는다
  - [ ] 답을 고를 때마다 같은 응답 ID로 저장 요청이 간다
  - [ ] 답 저장이 실패해도 설문은 계속 진행되고, 다음 저장에 그때까지의 답이 모두 실린다
  - [ ] 실제 API에 연결한 브라우저에서 두 번째 질문까지 답하고 닫으면 DB에 그 두 답이 이메일 없이 남고, 끝까지 등록하면 같은 응답에 이메일이 남는다
  - [ ] 이메일 저장이 실패하면 완료 화면이 나오지 않고 다시 시도할 수 있다
  - [ ] 화면 폭 860px 이하에서 한 단으로 바뀌고, 560px 이하에서 대화상자가 화면을 채운다
  - [ ] 기기가 다크 모드면 다크로 보인다
  - [ ] `pnpm lint && pnpm typecheck && pnpm test && pnpm build`가 통과한다
- **검증 방법:** 웹 컴포넌트 테스트(가짜 API), 로컬에서 web·api를 띄워 브라우저로 등록 확인(데스크톱·모바일 폭, 라이트·다크)
- **선행 Issue:** A
- **미결정 사항:** 없음 (D-16은 공개 배포 전에 필요하며 구현을 막지 않는다)
