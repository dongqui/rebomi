# 첫 개발 묶음 — Issue 초안 (등록 완료)

**상태: 2026-11-10 GitHub에 등록했다 — #1~#6 (초안 번호와 같다). 이후의 기준은 GitHub Issue이며 이 문서는 갱신하지 않는다.** 같은 날 인증 방식이 결정되어 #2는 실제 소셜 로그인(Google·Apple)으로 다시 썼고, 웹 로그인 화면 #7을 추가했다. 아래 초안 2와 "등록 전에 필요한 결정"은 등록 전의 내용이다.

## 묶음의 목표

**웹에서 URL 저장 → 목록에 즉시 표시 → 비동기 처리 상태가 바뀌는 것을 확인.** 스캐폴드가 증명한 경로(클라이언트 → api-client → api → db, api → pg-boss → worker)에 첫 실제 기능을 얹는다. 이후 모든 기능(요약, 검색, 재노출, 확장·모바일 저장)이 이 콘텐츠 리소스와 처리 파이프라인 위에 붙는다.

요약(LLM)은 넣지 않는다 — 제공자가 미정이고, 이 묶음의 "비동기 처리"는 메타데이터 수집과 서버 본문 추출까지다.

## 등록 전에 필요한 결정

초안 2가 **D-08(인증 방식)** 에 걸린다. 저장에는 사용자가 필요하다. 두 가지 길이 있다.

- **(가) D-08을 먼저 결정** → 초안 2를 실제 로그인 구현으로 바꾼다.
- **(나) [제안] 개발용 사용자 식별만 먼저** → 초안 2대로. `requireAuth`가 토큰으로 사용자를 찾는 인터페이스만 확정하고, 토큰은 시드 스크립트가 발급한다. 실제 회원가입·로그인은 D-08 결정 후 별도 Issue. API 계약(Bearer 토큰)은 바뀌지 않는다.

### 2. [api] 요청의 사용자 식별 (개발용) — **D-08에 따라 바뀜**

- **PRD:** `docs/features/account.md` §5 / `docs/architecture.md` §3
- **목표:** 콘텐츠 API가 요청한 사용자를 알 수 있게 한다.
- **포함:** `requireAuth`가 토큰을 검증해 사용자를 요청에 붙임, 개발용 사용자·토큰 시드 명령, 웹이 `getToken`으로 토큰 전달
- **제외:** 회원가입·로그인 화면, 소셜 로그인, 토큰 만료·갱신, 확장·모바일
- **완료 조건**
  - [ ] 토큰 없는 요청은 401 `UNAUTHORIZED`

  - [ ] 유효한 토큰의 요청 핸들러가 사용자 ID를 얻는다
  - [ ] 시드 명령으로 만든 토큰으로 로컬 웹이 인증된 요청을 보낸다
- **검증:** API 통합 테스트

### 3. [api] URL 저장과 목록 API

- **PRD:** `docs/features/capture.md` §2 CAP-1, CAP-6 / §4 흐름 3 · `docs/features/library.md` §2 LIB-1(목록·최근순만)
- **목표:** URL을 저장하고 내 콘텐츠 목록을 받는다.
- **포함:** 저장 엔드포인트(`core.normalizeUrl`로 정규화, 중복 감지, 저장 성공과 중복을 구분하는 응답), 목록 엔드포인트(본인 것만, 최근순), `api-client` 메서드, 저장 시 처리 잡 큐잉
- **제외:** 본문을 함께 받는 저장(확장·모바일), 정렬 옵션·필터·검색, 상태 변경, 한도 집행(D-03)
- **완료 조건**
  - [ ] 유효한 URL 저장 시 콘텐츠가 생기고 즉시 응답한다(처리 완료를 기다리지 않는다)
  - [ ] 트래킹 파라미터만 다른 URL의 두 번째 저장은 중복으로 응답하고 콘텐츠가 늘지 않는다
  - [ ] http(s)가 아닌 입력은 400 `VALIDATION_FAILED`
  - [ ] 목록은 요청한 사용자의 콘텐츠만 최근순으로 준다. 다른 사용자의 것은 나오지 않는다
  - [ ] 응답이 계약의 JSON 스키마로 직렬화된다
  - [ ] 저장하면 처리 잡이 큐에 들어간다
- **검증:** API 통합 테스트(실제 Postgres), `api-client` 단위 테스트
- **선행:** 1, 2 · **미결정:** 없음

### 4. [worker] 메타데이터 수집 잡과 처리 상태 전이

- **PRD:** `docs/features/capture.md` §2 CAP-5, CAP-7, CAP-8 / §5 본문 추출 우선순위(3·4순위) · `docs/architecture.md` §5
- **목표:** 저장된 URL을 서버가 가져와 제목·대표 이미지·본문을 채우고 추출 수준을 정한다.
- **포함:** 처리 잡(큐 이름은 `QUEUES`에), 페이지 fetch, 제목·OG 설명·대표 이미지 추출, 본문 추출 시도, 추출 수준 판정(본문 / 메타데이터만), 실패 시 재시도, 재시도 소진 시 상태 기록
- **제외:** 요약·임베딩, 링크 소멸 판정(D-04), YouTube 자막, 클라이언트가 보낸 본문 처리
- **완료 조건**
  - [ ] 공개 기사 URL은 처리 후 제목·도메인·대표 이미지가 채워지고 추출 수준이 "본문"이다
  - [ ] 본문을 못 얻은 URL은 "메타데이터만"이고 저장은 유지된다
  - [ ] 일시적 fetch 실패는 재시도된다
  - [ ] 재시도가 소진되면 처리 상태가 실패로 남고 워커는 계속 돈다
  - [ ] 처리 중·완료·실패를 API 응답으로 구분할 수 있다
- **검증:** 로컬 HTTP 픽스처 서버를 상대로 한 워커 통합 테스트(외부 사이트에 의존하지 않는다)
- **선행:** 1 (3과 병행 가능. 큐 이름·페이로드를 1에서 합의) · **미결정:** 본문 추출 라이브러리 선택은 설계에서(기술 결정)

## 재노출 가설(H2)은 언제 검증하나

원문은 H2를 Phase 3 완료 후 2차 테스트로 둔다. 판단 지표는 "재노출 콘텐츠 vs 미노출 콘텐츠의 **4주 내** 원문 열람률"이고, 선정 규칙은 **저장 7일 이상**을 요구한다. 그래서 재노출이 배포된 날부터 첫 신호까지 최소 1주, 판단까지 최소 5주가 걸린다.

**[제안]** 출시 범위와 Phase 게이트는 그대로 두고 구현 순서만 조정한다.

- 재노출 선정 규칙(순수 함수)과 웹 홈 피드를 요약 직후로 당겨, 팀이 자기 데이터로 먼저 쓴다.
- 노출·펼침·액션 계측을 재노출의 **첫 Issue**에 넣는다. 나중에 붙이면 그만큼 관찰 기간을 잃는다.
- 정식 H2 검증(2차 사용자 테스트)은 원문대로 Phase 3 끝에 한다. 당겨 만든 것은 그 테스트의 관찰 기간을 미리 확보하는 용도다.

이 제안은 D-05(재노출 기본값)가 정해져야 실행할 수 있다.
