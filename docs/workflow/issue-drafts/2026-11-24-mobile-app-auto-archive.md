# 여섯째 개발 묶음 — 모바일 로그인과 앱 뼈대 · 자동 보관과 영구 삭제 · Issue 초안

**상태: 등록됨 (2026-11-24).** 사용자가 승인했고 D-08의 로그인 방식을 함께 정했다. A → #43, B → #44, C → #45. C(#45)는 2026-11-25에 하지 않기로 해 닫았고, 30일 자동 보관·영구 삭제는 PRD에서 뺐다(library §2).

## 묶음의 목표

**서로 다른 앱을 건드리는 작업을 골라 워크트리에서 동시에 진행한다.** 모바일은 골격(`/health` 호출)뿐이라 로그인부터 세운다. 워커는 보관 상태의 시간 규칙(30일)을 채운다.

## 이 묶음을 고른 이유

- **동시에 진행할 수 있게 건드리는 곳을 나눴다.** 모바일 Issue는 `apps/mobile`과 잠금 파일(의존성 추가), 워커 Issue는 `apps/worker`·`packages/core`(필요하면 `packages/db`)만 건드린다. 계약(`api-contract`, `api-client`)은 어느 쪽도 바꾸지 않는다.
- **모바일은 P0인데 아무것도 없다.** 공유 저장(CAP-3, CAP-4)은 로그인 세션을 쓰므로(CAP-11) 로그인이 먼저다.
- **자동 보관·영구 삭제(LIB-2, LIB-4)**는 2026-11-18에 "보관함 화면 묶음으로 넘긴다"고 뺐던 것이다. 2026-11-24에 사용자가 이번 묶음에 넣기로 했다. 화면 없이도 검증된다 — 시간을 주입한 테스트로 상태가 바뀌는 것을 본다.
- **웹은 이번 묶음에 Issue가 없다.** 처음에는 "자세히 보기 패널과 홈 최근 저장에서의 보관·삭제"를 후보로 냈으나 디자인을 다시 읽어 보니 근거가 없었다.
  - 디자인의 홈 최근 저장 행에는 "원문 보기"만 있다. 보관·삭제가 없다.
  - "자세히 보기"는 재노출 카드에서만 열린다. 검색 결과 행에는 없다. 재노출 카드는 아직 없다(D-05).
  - 보관함·Inbox·휴지통 화면은 디자인이 여전히 "이어서 설계해요"다.
- **확장은 P0 기능이 끝났다**(#18, #20). 남은 것은 스토어 등록과 운영 빌드이고 API 배포와 개인정보처리방침이 먼저 있어야 한다.
- 다른 후보는 먼저 정해져야 할 것이 있다: 요약(LLM 제공자, D-13, D-12), 재노출(D-05, D-11), 의미 검색(`2026-11-18-semantic-search.md`의 "먼저 정할 것"), 가져오기(D-03, D-04).

## 권장 순서

`(#43 → #44) ∥ #45`

A와 C는 서로 기대지 않고 건드리는 곳이 겹치지 않는다 — 워크트리 둘로 동시에 간다. B는 A 뒤에 같은 갈래에서 이어서 한다.

**동시에 진행할 때의 규칙**

- 의존성 추가(잠금 파일)는 모바일 갈래만, DB 마이그레이션은 워커 갈래만 한다.

- 로컬 Postgres가 하나다. DB를 쓰는 테스트(`api`, `db`, `worker`, `e2e`, `web`의 서버 테스트)는 워커 갈래에서만 돌리고, 모바일 갈래는 자기 패키지의 검사만 돌린다. 전체 검사는 CI가 한다.

## 이월한 완료 조건

- **iOS에서의 로그인·화면 확인** (account §5-1, §5-2) → iOS를 빌드할 수 있을 때(Mac 또는 EAS). A와 B는 iOS 코드를 쓰고 타입 검사까지만 한다.
