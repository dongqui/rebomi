# 대기 명단 랜딩 (waitlist)

원본: PRD v0.5에는 없다. 2026-11-17에 추가했다. 화면과 문구의 기준은 디자인 프로젝트의 `RebomiLanding`이다 · 공통 규칙: [architecture §8 개인정보](../architecture.md#8-개인정보)

> 기본 문서 구조에 없던 문서다. 제품 기능(P0)이 아니라 출시 전에 수요를 확인하는 광고 랜딩이고, 들어갈 자리가 없어 만들었다.

## 1. 목적

Rebomi가 열리기 전에 광고로 들어온 방문자에게 무엇을 만드는지 보여 주고, 관심 있는 사람의 이메일과 저장 습관에 대한 짧은 답을 받는다. 답은 수요와 지불 의향을 판단하는 데 쓴다. 의견을 최대한 모으는 것이 목적이므로, 끝까지 가지 않은 방문자의 답도 남긴다.

## 2. 범위

**포함**

| ID | 요구사항 |
| --- | --- |
| WAIT-1 | 웹의 첫 주소(`/`)는 로그인 여부와 무관하게 랜딩 페이지다. 로그인한 사용자의 화면(지금의 저장·목록)은 `/app`에 있다 |
| WAIT-2 | 랜딩은 디자인의 구성을 따른다: 히어로(헤드라인, 설명, 등록 버튼, 휴대폰 화면), 문제 제기, 하는 일 세 가지, "차분하게", 사용 방법, 마지막 등록 버튼, 푸터 |
| WAIT-3 | 등록 버튼을 누르면 대화상자가 열려 질문 네 개 → 이메일 → 완료 순으로 진행한다. 이전 단계로 돌아갈 수 있고, 닫았다 다시 열면 하던 단계에서 이어진다 |
| WAIT-4 | 이메일을 내면 그 응답에 이메일이 저장된다. 저장에 성공한 뒤에만 완료 화면을 보여 준다 |
| WAIT-5 | 한국어와 영어를 지원한다. 브라우저 언어가 한국어면 한국어, 그 밖에는 영어로 보여 준다 |
| WAIT-6 | 헤드라인은 세 가지(저장하고 잊음 / 여기저기 흩어짐 / 찾을 수 없음)이고 광고 소재에 맞춰 주소로 고른다. 지정이 없으면 "저장하고 잊음"이다 |
| WAIT-7 | 라이트·다크는 기기 설정을 따른다 |
| WAIT-8 | 설문의 답은 고를 때마다 서버에 저장된다. 이메일까지 가지 않고 그만둔 방문자의 답도 남는다 |

**제외**

- 대화상자를 열기만 하고 아무것도 고르지 않은 방문의 기록, 광고 유입 파라미터의 기록 (D-17)
- 등록 확인 메일, 초대 메일 발송
- 히어로 휴대폰 안 화면의 조작 — 디자인은 조작 가능한 모바일 목업을 넣었으나, 랜딩에는 첫 화면(재노출 카드)을 정적으로 그린다 (2026-11-17)
- 랜딩에서의 로그인·가입 진입점 — 디자인에 없다

## 3. 플랫폼별 역할

| 플랫폼 | 역할 |
| --- | --- |
| 서버 | 설문 응답 저장 API(인증 없음): 응답 생성·갱신, 이메일 저장 |
| 웹 | 랜딩 페이지, 등록 대화상자, 로그인한 화면의 `/app` 이전 |
| 확장·모바일 | 없음 |

## 4. 사용자 흐름

1. 방문자가 광고를 눌러 `/`에 온다. 주소에 헤드라인 지정이 있으면 그 헤드라인을 본다.
2. 등록 버튼을 누른다. 대화상자가 첫 질문으로 열리고, 이 응답의 ID가 브라우저에서 만들어진다. 이때는 아직 서버에 아무것도 없다.
3. 첫 질문에서 선택지를 고른다. 그 ID로 서버에 응답이 만들어진다.
4. 나머지 질문에 답한다. 고를 때마다(여러 개를 고르는 질문은 고르거나 뺄 때마다) 같은 응답이 갱신된다. 여러 개를 고르는 질문은 "다음"으로, 하나만 고르는 질문은 고르면 바로 넘어간다.
5. 이메일을 적고 등록한다. 형식이 틀리면 그 자리에서 알린다.
6. 서버가 같은 응답에 이메일을 저장하면 완료 화면을 본다. 저장에 실패하면 이메일 단계에 머물고 다시 시도할 수 있다.

## 5. 동작 규칙

**결정된 것 (2026-11-17)**

- `/`는 항상 랜딩이다. 로그인 확인을 기다리지 않고 바로 뜬다. 로그인한 화면은 `/app`으로 옮기고, 로그인 뒤의 이동과 로그인이 필요한 화면의 보호도 `/app` 기준으로 바꾼다.
- 이메일과 설문 답을 서버에 저장한다.
- 언어는 브라우저 언어로 고른다.
- 휴대폰 화면은 정적이다.
- 톤은 디자인 기본값인 "웜 페이퍼"다.

**결정된 것 (2026-11-17, 같은 날 뒤에 바꿈)**

- 설문의 답은 고를 때마다 저장한다(WAIT-8). 대화상자가 열릴 때 브라우저가 응답 ID를 만들고, 첫 답을 고르는 순간 그 ID로 서버에 응답이 생기며, 이후의 답과 이메일은 같은 응답을 갱신한다. 어디까지 답했는지는 응답에 남은 답으로 알 수 있다.
- 답을 저장하는 요청이 실패해도 설문 진행을 막지 않는다. 방문자에게 오류를 보이지 않고 다음 답을 저장할 때 지금까지의 답을 함께 보낸다. 이메일 저장의 실패만 방문자에게 알린다(WAIT-4).
- 같은 이메일로 여러 번 등록할 수 있다. 응답마다 따로 남고, 이메일로 묶거나 막지 않는다.

**그 밖의 규칙**

- 질문과 선택지의 문구·순서는 디자인을 따른다. 질문은 넷이다: 저장물이 쌓이는 곳(복수 선택), 다시 보는 빈도, 가장 도움이 될 것, 지불 의향.
- 답은 문구가 아니라 언어와 무관한 고정 키로 저장한다 — 한국어와 영어 응답을 함께 집계할 수 있어야 한다.
- 어느 언어와 어느 헤드라인으로 등록했는지 함께 저장한다 (광고 소재별 비교).
- 이메일은 앞뒤 공백을 떼고 대소문자를 구분하지 않는다 ([account](account.md) §4와 같다).
- **[제안]** 응답 저장 API는 인증이 없고 이메일 없이도 응답을 만들 수 있으므로 같은 출처의 과도한 요청을 제한한다. 방식은 구현 Issue의 설계에서 정한다.
- **[제안]** 응답 ID를 아는 쪽만 그 응답을 갱신할 수 있고, API는 저장된 응답을 돌려주지 않는다(남의 이메일과 답을 읽을 길이 없다).
- **[확인 필요]** 완료 화면을 본 뒤 같은 페이지에서 등록 버튼을 다시 누르면 새 응답으로 시작하는지, 완료 화면을 다시 보여 주는지 — 구현 Issue의 설계에서 묻는다.
- 대기 명단 이메일은 계정이 아니다. 이 이메일로 `users` 행을 만들지 않고, 나중에 그 이메일로 가입해도 자동으로 연결하지 않는다.

## 6. 완료 조건

- [ ] 로그인하지 않은 브라우저로 `/`를 열면 로그인 화면으로 넘어가지 않고 랜딩이 보인다.
- [ ] 로그인한 사용자는 `/app`에서 저장과 목록을 지금과 똑같이 쓴다. 로그인하지 않고 `/app`을 열면 로그인 화면으로 간다. 로그인에 성공하면 `/app`으로 간다.
- [ ] 브라우저 언어가 한국어면 한국어 문구, 아니면 영어 문구가 보인다.
- [ ] 주소로 헤드라인을 지정하면 그 헤드라인이, 지정이 없거나 모르는 값이면 기본 헤드라인이 보인다.
- [ ] 등록 버튼 → 질문 네 개 → 이메일 → 완료까지 키보드만으로 진행할 수 있다.
- [ ] 이메일 형식이 틀리면 서버로 보내지 않고 그 자리에서 알린다.
- [ ] 대화상자를 열기만 하고 닫으면 DB에 아무것도 남지 않는다.
- [ ] 첫 질문에 답하면 응답이 DB에 생기고, 답을 고르거나 바꿀 때마다 같은 응답이 갱신된다. 언어와 헤드라인도 함께 남는다.
- [ ] 두 번째 질문까지 답하고 닫으면 그 두 답이 이메일 없이 DB에 남는다.
- [ ] 이메일을 내면 같은 응답에 이메일이 남는다. 응답이 하나 더 생기지 않는다.
- [ ] 이메일 저장이 실패하면 완료 화면이 나오지 않고, 다시 시도할 수 있다.
- [ ] 답 저장이 실패해도 설문은 계속 진행되고, 다음 저장이 성공하면 그때까지의 답이 모두 남는다.
- [ ] 같은 이메일로 두 번 등록하면 응답이 두 개 남는다.
- [ ] 화면 폭 860px 이하에서 한 단으로 바뀌고, 560px 이하에서 대화상자가 화면을 채운다 (디자인 기준).

## 7. 의존

- [account](account.md) — 로그인한 화면의 주소가 바뀐다(`/` → `/app`). 로그인 방식과 세션은 그대로다.
- Apple 로그인의 Return URL(`/login`)은 바뀌지 않는다.

## 8. 미결정

- **D-16** 대기 명단 이메일 수집의 고지와 보관 — 공개 배포 전에 필요하다. 구현은 막지 않는다.
- **D-17** 설문에 답하지 않은 방문과 광고 유입의 계측
