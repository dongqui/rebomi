# 계정과 동기화 (account)

원본: PRD v0.5 §3.2~3.3(계정 동기화, 세션 공유), §4.1(기기 간 동기화), §5.6(설정), §6(계정 P0), §11.8 · 공통 규칙: [architecture §3 인증](../architecture.md#3-인증과-기기-동기화)

> 기본 문서 구조에는 없던 문서다. 6장 P0의 "회원가입, 로그인, 기기 간 동기화"와 5.6의 내보내기·삭제가 들어갈 자리가 없어 만들었다. 로그인 방식은 원문에 없었고 2026-11-10에 결정했다(§4).

## 1. 목적

어느 기기에서 저장하든 같은 계정의 콘텐츠로 모이게 한다. 사용자의 데이터는 본인만 본다.

## 2. 범위

**P0 포함**

| ID | 요구사항 |
| --- | --- |
| ACC-1 | 회원가입한다. 별도 가입 절차 없이 첫 소셜 로그인이 계정을 만든다 |
| ACC-2 | Google 또는 Apple 계정으로 로그인한다. 웹, Chrome 확장, iOS, Android 모두에서 같은 계정을 쓴다 |
| ACC-3 | 기기 간 동기화: 한 기기에서 저장·변경한 것이 같은 계정의 다른 기기에 나타난다 |
| ACC-6 | 로그인 상태는 만료가 있는 액세스 토큰과 갱신 토큰으로 유지한다. 액세스 토큰이 만료되면 사용자 조작 없이 갱신된다 |
| ACC-7 | Google과 Apple이 검증한 이메일이 같으면 같은 계정이다 |
| ACC-8 | 로그아웃한다 |

**출시 범위 미정 (D-06)**

| ID | 요구사항 |
| --- | --- |
| ACC-4 | 데이터를 내보낸다 |
| ACC-5 | 계정과 데이터를 삭제한다 |

원문 §5.6 설정과 §11.8 대응에는 있으나 §6 P0 표에는 없다. 임의로 P0·P1 어느 쪽으로도 확정하지 않는다.

**제외**

- 이메일+비밀번호 로그인, 매직 링크
- 외부 인증 서비스 — 인증은 직접 구현한다
- 사용자가 설정에서 계정을 수동으로 연결·분리하는 기능

## 3. 플랫폼별 역할

| 플랫폼 | 역할 |
| --- | --- |
| 서버 | Google·Apple이 발급한 신원 토큰 검증, 계정 생성·조회, 액세스·갱신 토큰 발급과 갱신·폐기, 사용자별 접근 제한 |
| 웹 | 로그인 화면(Google, Apple), 토큰 보관과 자동 갱신, 로그아웃, 설정의 계정 항목 |
| 확장 | 로그인 상태 확인, 토큰 보관(`chrome.storage`) — 로그인 방식은 D-08 |
| 모바일 | 로그인 화면, 토큰 보관(`SecureStore`), 공유 확장과 세션 공유(iOS App Group, Android 공유 저장소) |

## 4. 동작 규칙

**결정된 것 (2026-11-10)**

- 인증은 외부 서비스 없이 직접 구현한다.
- 로그인 수단은 소셜 로그인 두 가지다: Google, Apple.
- 세션은 만료가 있는 액세스 토큰 + 갱신 토큰이다. API는 `Authorization: Bearer <액세스 토큰>`을 받는다.
- 두 제공자가 검증한 이메일이 같으면 자동으로 같은 계정이다. Apple의 "이메일 숨기기"를 쓴 경우는 이메일이 달라 별도 계정이 된다.
- 개발용 임시 인증을 따로 두지 않고 처음부터 실제 로그인으로 구현한다.

**결정된 것 (2026-11-11)**

- 처음 보는 신원인데 제공자가 검증한 이메일이 없으면(미검증이라고 알려 왔거나 이메일을 주지 않음) 로그인을 거부한다. 이메일 없는 계정은 만들지 않는다. 이미 가입한 신원은 그대로 로그인된다.
- 웹은 갱신 토큰을 스크립트가 읽을 수 없는 httpOnly 쿠키로 받는다. 확장과 모바일은 응답 본문으로 받아 각자의 저장소에 둔다. 웹과 API가 같은 사이트(같은 등록 도메인)에 배포되는 것이 전제다.
- 인증 실패는 원인별 에러 코드로 구분한다. 코드 목록은 [architecture §3](../architecture.md#3-인증과-기기-동기화)에 있다.

**그 밖의 규칙**

- 모든 콘텐츠는 비공개 기본값이고 소유 사용자만 접근한다.
- 공유 확장은 메인 앱의 로그인 세션을 그대로 쓴다. 공유창에서 다시 로그인하게 하지 않는다.
- 제공자가 이메일을 검증하지 않았다고 알려 온 경우에는 이메일로 계정을 묶지 않는다(ACC-7은 검증된 이메일에만 적용한다).
- 이메일은 대소문자를 구분하지 않고 비교한다.
- 토큰의 수명, 저장 형태, 서명 방식은 기술 결정이고 [architecture §3](../architecture.md#3-인증과-기기-동기화)에 기록돼 있다.

## 5. 완료 조건

- [ ] Google 계정으로 처음 로그인하면 계정이 만들어지고 로그인된다. 다시 로그인하면 같은 계정이다.
- [ ] Apple 계정으로도 위와 같다.
- [ ] Google로 만든 계정과 검증된 이메일이 같은 Apple 계정으로 로그인하면 같은 계정의 콘텐츠가 보인다.
- [ ] 이메일이 다른 두 로그인은 서로 다른 계정이다.
- [ ] 위조되었거나 만료된 제공자 토큰, 다른 앱에 발급된 제공자 토큰으로는 로그인할 수 없다.
- [ ] 로그인하지 않은 요청은 콘텐츠 API에서 401 `UNAUTHORIZED`를 받는다.
- [ ] 액세스 토큰이 만료되면 갱신 토큰으로 새 액세스 토큰을 받고, 사용자는 다시 로그인하지 않는다.
- [ ] 갱신 토큰이 만료·폐기되면 로그인 화면으로 돌아간다.
- [ ] 로그아웃하면 그 기기의 갱신 토큰이 더 이상 쓰이지 않는다.
- [ ] 사용자 A의 토큰으로 사용자 B의 콘텐츠를 조회·수정·삭제할 수 없다.
- [ ] 한 기기에서 저장한 콘텐츠가 같은 계정의 다른 클라이언트 목록에 나타난다.
- [ ] iOS·Android 공유 확장이 메인 앱의 로그인 상태로 저장한다.
- [ ] 토큰과 제공자 비밀값이 저장소와 로그에 남지 않는다.

## 6. 의존

모든 기능이 이 문서에 의존한다. 서버의 로그인·갱신·로그아웃과 `requireAuth`, `api-client`의 자동 갱신은 구현돼 있다(Issue #2). 로그인 화면과 각 클라이언트의 토큰 보관은 아직 없다.

실제 계정으로 로그인하려면 사용자가 준비할 외부 설정이 필요하다: Google OAuth 클라이언트 ID, Apple Developer 계정의 Service ID(웹)와 앱 번들 ID(iOS). 서버는 제공자의 신원 토큰만 검증하므로 Apple 비밀키는 서버에 두지 않는다.

## 7. 미결정

- **D-08** (남은 부분) 확장의 로그인 방식(웹 세션 재사용 여부), 모바일에서의 로그인 흐름 세부, "동기화"의 반영 시점(다음 조회 시 / 실시간)
- **D-06** 내보내기·삭제의 출시 범위, 내보내기 형식
