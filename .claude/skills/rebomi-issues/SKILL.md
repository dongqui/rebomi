# Rebomi PRD → GitHub Issue

지정된 기능 또는 단계의 요구사항을 **독립적으로 검증·리뷰할 수 있는 작업**으로 나누어 GitHub에 실제 Issue로 등록한다.

**REQUIRED:** 시작할 때 `docs/workflow/github.md`를 읽는다. 도구 확인, 라벨, Issue 형식, 중복 표식이 거기 있다.

## 등록인가 초안인가

| 사용자의 말 | 동작 |
| --- | --- |
| "등록해줘", "이슈 만들어줘", "올려줘" | **실제로 등록한다.** 초안을 보여주고 허락을 다시 묻지 않는다 |
| "초안", "제안", "어떻게 나눌지 보여줘" | 등록하지 않는다. `docs/workflow/issue-drafts/YYYY-MM-DD-<범위>.md`에 쓴다 |

등록 요청을 받았는데 GitHub에 쓸 수 없으면(MCP도 `gh`도 없음) 로컬 초안을 만들고, 등록하지 못했다는 것과 기존 Issue를 확인하지 못했다는 것을 분명히 말한다.

## 절차

1. **전제 확인** — Issue가 참조할 문서(`docs/features/…`, `docs/architecture.md`)가 `origin/main`에 있는지 본다(`git ls-tree origin/main`). 없으면 Issue의 PRD 참조가 GitHub에서 깨지고 실행 브랜치에도 문서가 없다. 등록을 멈추고 문서를 먼저 push해야 한다고 알린다.
2. **범위 고정** — 사용자가 지정한 기능·단계만 분해한다. 전체 P0를 한 번에 수십 개로 쪼개지 않는다.
3. **기존 초안 확인** — `docs/workflow/issue-drafts/`에 이 범위의 초안이 있으면 그것을 출발점으로 삼는다. 사용자가 본 분해를 버리고 새로 나누지 않는다. 초안 이후 바뀐 것(코드, 결정)만 반영한다.
4. **읽기** — 해당 `docs/features/<기능>.md` 전체, 그 문서가 링크한 공통 규칙 절, `product.md` §9의 관련 D-xx 행. 요구사항이 다른 기능 문서의 ID를 인용하면(`CAP-6과 같은 규칙`) 그 문서의 그 절만 읽는다. 인용되지 않은 기능 문서에서 시작하지 않는다.
5. **구현 확인** — 관련 코드를 본다(`architecture.md` §1이 출발점). 이미 있는 것을 다시 만드는 Issue를 내지 않는다. 스캐폴드가 있다는 것은 기능이 구현됐다는 뜻이 아니다.
6. **기존 Issue 확인** — 열린 것과 **닫힌 것 모두** 조회한다. 제목 핵심어와 요구사항 ID로 찾는다.
   - **중복**은 영역(제목의 `[api]`)과 목표가 같은 Issue다. 요구사항 ID가 겹치는 것만으로는 중복이 아니다 — 한 요구사항이 계약·서버·화면 Issue로 나뉜다.
   - 중복이면 만들지 않고 그 번호를 보고에 넣는다. 일부만 겹치면 겹치지 않는 부분만 만든다.
   - 도중에 실패해 다시 돌릴 때는 이미 만들어진 것을 제목으로 대조하고 나머지만 만든다.
7. **분해** — 아래 기준.
8. **등록** — 선행 관계의 위상 순서로 만든다. 첫 Issue를 만든 직후 다시 조회해 제목·라벨·표식을 확인한 다음 나머지를 만든다.
9. **보고** — 아래 형식.

## 분해 기준

나누는 기준은 파일 수나 예상 시간이 아니라 **혼자서 검증되고 리뷰되는 결과**다.

- 완료 조건은 기능 문서의 완료 조건에서 가져온다. 마지막에 기능 문서의 완료 조건을 하나씩 대조해 어느 Issue에 배정됐는지 확인한다.
- 서버·클라이언트가 공유하는 API·상태 계약(`packages/api-contract`, DB 스키마)이 필요하면 선행 Issue로 두거나 선행 Issue의 완료 조건에 넣는다.
- 서버와 클라이언트를 나눴으면 **실제로 연결해 검증하는 작업**이 어딘가에 있어야 한다.
- 테스트를 마지막 Issue 하나로 몰지 않는다. 각 Issue가 자기 완료 조건을 검증한다.
- 플랫폼별 작업은 Issue로 나눈다. 모든 기능에 네 플랫폼이 다 필요하지는 않다 — 기능 문서의 "플랫폼별 역할" 표를 따른다.
- 계측이 완료 조건에 있으면 그 동작을 만드는 Issue에 넣는다.
- 본문에 구현 절차를 길게 쓰지 않는다. 설계와 계획은 실행할 때 Superpowers가 만든다.

**이 범위 밖의 것에 기대는 경우**

| 상황 | 처리 |
| --- | --- |
| 다른 기능의 결과물이 먼저 있어야 한다(콘텐츠 테이블, 인증, 목록…) — 그 Issue가 이미 있다 | "선행 Issue"에 번호로 적는다 |
| 그 Issue가 아직 없다 | "선행 Issue"에 `- (미등록) 무엇 — docs/features/<문서> <ID>`로 적는다. **"없음"으로 쓰지 않는다.** 대신 만들지도 않는다(범위 밖). 보고의 "미등록 선행"에 모아 사용자가 그 기능의 등록을 요청할 수 있게 한다 |
| 완료 조건이 다른 기능이 있어야만 검증된다(가져온 북마크가 검색에 잡힌다, 피드에 나오지 않는다) | 지금 검증할 수 있는 부분만 이 범위의 Issue에 넣고, 나머지는 보고의 "이월한 완료 조건"에 어느 기능을 분해할 때 가져가야 하는지와 함께 적는다 |
| 요구사항 ID가 없는 규칙(다른 문서의 한도 등)을 다룬다 | 표식과 PRD 참조에 그 규칙이 실제로 있는 문서와 ID를 쓴다(`billing.md BILL-2`) |

## 정책이 미정일 때

완료 조건이 **`product.md` §9의 D-xx** 또는 **기능 문서의 `[확인 필요]`·"미결정" 항목**에 달려 있으면:

- 그 Issue를 **`needs-decision` 라벨로 등록**하고(`status:todo` 대신) "미결정 사항"에 근거 위치(`D-03`, 또는 `import.md §8 저장일 기준`)와 무엇이 정해져야 하는지 적는다. 등록을 건너뛰지 않는다.
- **정책을 임의로 정해 완료 조건이나 범위에 써넣지 않는다.** "일단 ~까지만 한다" 같은 임시 정책도 마찬가지다. 구현자에게 판단을 넘기지도 않는다.
- 결정과 무관한 부분을 떼어 낼 수 있으면 그 부분은 `status:todo` Issue로 만든다.
- 관련 없는 Issue까지 멈추지 않는다.

어느 문서에도 적혀 있지 않은 정책 공백을 새로 발견하면, 보고에 적고 `rebomi-prd`로 `product.md` §9에 올릴지 사용자에게 묻는다. 등록 도중에 PRD를 고치지 않는다.

## 보고 형식

```
등록 N건: 지금 실행 가능 a · 선행 대기 b · 결정 대기(needs-decision) c
건너뜀: 기존 Issue와 중복 d건 (#…)

| # | 제목 | 라벨 | 선행 | 요구사항 |
| #12 링크 | [contract] … | status:todo | 없음 | CAP-5, CAP-7 |

권장 실행 순서: #12 → #13 → (#14, #15 병행) → #16
결정 대기: #17 — D-03 (저장 한도 초과 시 동작)
미등록 선행: 콘텐츠 리소스 계약 (capture CAP-5) — #12, #13이 기다림
이월한 완료 조건: import §6-3 "키워드 검색에 잡힌다" → search 분해 시
```

MCP가 없어 `gh`로 등록했으면 그 사실을 한 줄 적는다.
